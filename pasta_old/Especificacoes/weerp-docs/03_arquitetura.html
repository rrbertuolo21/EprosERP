Arquitetura técnica

Tudo que define como o Epros é construído, operado e evoluído — da decisão de monólito modular ao pipeline SecDevOps, passando por testes, padrões de desenvolvimento e frameworks de governança de TI.

Veredicto — Monólito Modular vs Microserviços
Escolha: Monólito Modular + Hexagonal por bounded context. Transações ACID nativas (PCI), audit log centralizado (LGPD), time pequeno foca em produto. Microserviços na fase 2 via extração cirúrgica — sem reescrever nada.

Por que não é um monólito comum

Schema próprio por macrodomínio

Cada módulo tem schema PostgreSQL próprio (financas.*, vendas.*…). Extração futura em microserviço não move dados — a fronteira lógica de hoje é a física de amanhã.

Interfaces públicas explícitas

Módulos expõem apenas Application interfaces. Nenhum handler de Vendas acessa repositório de Estoque. Violação bloqueia o PR.

Comunicação só via Domain Events

Contratos de evento idênticos aos que Kafka/RabbitMQ usariam. Migração na fase 2 sem reescrever nada — só troca o transporte.

7 middlewares — ordem de execução
1
UseAuthentication / UseAuthorization Auth
JWT Bearer via Keycloak 24. Valida token, injeta claims. 401 se inválido ou expirado.
2
ExcecaoGlobalMiddleware PX-003
Captura todas as exceções. Retorna ProblemDetails (RFC 7807) com TraceId. Nunca expõe stack trace em produção.
3
InquilinoSaaSMiddleware Multi-tenant
Resolve tenant via claim JWT. Valida no Catalog DB (cache Valkey 5min). Enriquece Serilog com tenantId para correlação total dos logs.
4
ModuloTenantMiddleware Entitlement
Verifica macrodomínio + submódulo ativo para o tenant. 403 Forbidden se inativo. Zero custo para módulos desabilitados.
5
DataMaskingMiddleware PCI
Mascara CPF, CNPJ, PAN, dados bancários antes de qualquer Serilog sink. Atributo [Sensitive] nas entidades. PCI DSS Req. 3.
6
AuditMiddleware LGPD
Persiste quem, o quê, quando, IP e tenant em tabela audit_trail append-only. Triggers PG bloqueiam UPDATE/DELETE. LGPD art. 37 + PCI DSS Req. 10.
7
Controllers Business
Executa via MediatR.Send(command). Zero lógica de negócio — apenas serialização e roteamento.

7 princípios invioláveis
01

Fronteiras de módulo são técnicas, não organizacionais

Módulos expõem apenas interfaces públicas. Nenhum handler acessa DbContext de outro módulo. Cross-schema queries explícitas e documentadas. Violação = bloqueio de merge.

02

Schema próprio por macrodomínio no PostgreSQL

Tabelas vivem em financas.*, estoque.*, vendas.*… A fronteira lógica de hoje é a fronteira física de quando extrairmos em microserviços — sem migração de dados.

03

Outbox Pattern para todos os Domain Events

Nenhum evento via fire-and-forget. Persistido em outbox_events na mesma transação. Worker Quartz.NET com retry exponencial. Zero perda de evento mesmo com falha de infra após SaveChanges.

04

Dados sensíveis nunca em texto livre no log

CPF, CNPJ, PAN, dados bancários passam pelo DataMaskingMiddleware antes de qualquer Serilog sink. Atributo [Sensitive] nas propriedades. PCI DSS Req. 3 — inegociável.

05

Toda ação sensível gera trilha imutável

AuditMiddleware persiste quem, o quê, quando, IP, tenant em audit_trail append-only. Triggers PG bloqueiam UPDATE e DELETE — imutabilidade no banco, não só na aplicação.

06

Multi-tenancy validado em três camadas independentes

Middleware (resolve) → QueryFilter EF Core (filtra) → Testcontainers (cenário A/B tenant leak é suite obrigatória no CI). Falha em qualquer camada = deploy bloqueado.

07

Secrets nunca no código ou appsettings de produção

JWT keys, connection strings, certificados — todos em HashiCorp Vault com dynamic secrets. Secret commitado = alerta automático no CI com bloqueio de merge.

Paradigmas e padrões adotados
DDD — Domain-Driven Design

Linguagem ubíqua por bounded context

Cada macrodomínio tem seu próprio modelo de domínio e linguagem. Entidades ricas com regras encapsuladas — sem anemic domain model. Aggregates, Value Objects e Domain Events como cidadãos de primeira classe.

CQRS — Command Query Responsibility Segregation

Escrita e leitura completamente separadas

Commands mudam estado e retornam CommandResult. Queries nunca mudam estado e retornam DTOs. Handlers são a única unidade testável de lógica. Controllers são roteadores puros.

TDD — Test-Driven Development

Testes antes do código de produção

Red → Green → Refactor. Testes unitários de domínio escritos antes da implementação. Facilita design emergente — código difícil de testar indica design ruim. Cobertura mínima 80% em lógica de negócio.

Hexagonal Architecture (Ports & Adapters)

Core isolado de infra e apresentação

Domain e Application nunca dependem de EF Core, HTTP ou banco. Adapters (Infrastructure) implementam as Ports (Interfaces) definidas pelo Application. Permite trocar banco ou framework sem mudar regras de negócio.

ADR — Architecture Decision Records

Como documentar uma decisão

Toda decisão arquitetural relevante deve ser documentada em docs/adr/ADR-{N}-{titulo}.md com: contexto, opções avaliadas, decisão tomada, racional, consequências e data. Vive no repositório junto ao código. Nunca retroativo em batch — máximo 48h após a decisão.

Pirâmide de testes
① Unit Tests Regras de negócio no domínio — EntidadeSaaSBase, agregados, Value Objects, CommandResult. Sem banco, sem HTTP, sem DI. Rápidos: <1ms por teste. xUnit puro. ~70% da cobertura
② Integration Tests Handlers + Repositories + banco PostgreSQL real via Testcontainers. Valida QueryFilter multi-tenant, soft delete, OutboxMessage, migrations. <5s por teste. ~25% da cobertura
③ E2E Tests Fluxos críticos de negócio completos — Playwright rodando contra a API real com banco Testcontainers. Ex: venda → NF-e → ContaReceber. Cenários de tenant leak. ~5% da cobertura
④ Performance k6 contra ambiente de staging com dados reais de volume. SLOs definidos: P95 <200ms para leitura, <500ms para escrita. Regressão de performance bloqueia deploy. SLO gates

Por que aqui e não na página de Compliance
Distinção importante: a página ⑤ Compliance trata de regulações de proteção de dados e privacidade (LGPD, GDPR, PCI DSS…). Esta aba trata de frameworks de governança de TI — padrões que definem como a área de tecnologia é gerida, auditada e opera em continuidade. São complementares, não redundantes.
3 frameworks de governança de TI
ISO/IEC 27001:2022Information Security Management System (ISMS)
Framework internacional de gestão de segurança da informação. Define 93 controles organizados em 4 temas: organizacional, pessoas, físico e tecnológico. Certificação auditada por terceiros.

Por que é relevante para o Epros: clientes Enterprise e regulados (BACEN, ANVISA) frequentemente exigem ISO 27001 como pré-requisito de contratação. A certificação valida que todo o processo — não apenas o código — é seguro.

ITIL 4IT Infrastructure Library — gestão de serviços de TI
Framework de boas práticas para gestão de serviços de TI. Foca no ciclo de vida do serviço: estratégia, design, transição, operação e melhoria contínua. ITIL 4 introduz o conceito de SVS (Service Value System) e as 4 dimensões.

Por que é relevante: define como entregar e operar o Epros como serviço gerenciado para clientes Enterprise — SLAs, gestão de incidentes, mudanças e capacidade.

Como os 3 frameworks se complementam

ISO 27001 → O QUE proteger

Define os controles de segurança que devem existir. Responde: "Nossos ativos de informação estão protegidos corretamente?"

ITIL 4 → COMO operar

Define como entregar e operar os serviços de TI com qualidade. Responde: "Estamos entregando valor de TI de forma consistente e previsível?"

COBIT 2019 → POR QUÊ e para QUEM

Define como a TI se alinha ao negócio e é governada. Responde: "A TI está entregando o valor que o negócio precisa com risco aceitável?"
