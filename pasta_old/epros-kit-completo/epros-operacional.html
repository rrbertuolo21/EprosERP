Novo Modelo › Papéis & Responsabilidades
Novo Modelo de Papéis
Sem contratar ninguém novo — redistribuição de responsabilidades com suporte dos agentes IA para cobrir os gaps.
Princípio: cada pessoa tem um papel principal claro. O Sênior para de ser PO. O dev de 10 anos vira Guardião de Domínio. Os agentes IA cobrem o que falta de capacidade — não substituem pessoas, amplificam.

Novo Modelo › IA no Dia a Dia
Como a IA Entra no Trabalho
Não é sobre substituir — é sobre amplificar. Cada função usa o agente certo no momento certo. O Context Agent é a base de tudo.
Passo zero (antes de qualquer outra coisa): configurar o arquivo .cursorrules na raiz do repositório PlataformaSaaS/ com o prompt do Context Agent. Isso injeta todo o domain knowledge do Epros em cada agente automaticamente. Prompts completos em epros-agentes-prompts.md.

📋
Requirements Agent
Quando: Antes do planning
Cola o rascunho de requisito ou a descrição do problema. Agente retorna US com ACs em Given/When/Then, riscos e dependências. Revisa, ajusta, apresenta para o time.
→ PO / Facilitador
📋
Planning Agent
Quando: Durante o planning
Cola a US finalizada. Agente quebra em tasks técnicas estimáveis, mapeia dependências e identifica impactos em multi-tenancy ou fiscal. Time valida.
→ PO / Facilitador
🏗️
Architect Agent
Quando: Antes de qualquer feature nova
Cola a proposta técnica ou o problema a resolver. Agente revisa contra os padrões Epros (.NET, CQRS, DDD, PostgreSQL) e retorna análise com alternativas e ADR sugerido.
→ Tech Lead
💻
Dev Agent (Cursor nativo)
Quando: Durante o coding
Context Agent via .cursorrules está sempre ativo. Cursor Tab autocompleta respeitando EntidadeSaaSBase, snake_case, Guid. Cursor Chat para dúvidas específicas de padrão.
→ Dev Backend
💻🎨
Code Review Agent
Quando: Antes de abrir o PR
Cola o diff completo. Agente retorna review com severidades: 🔴 bloqueante / 🟡 aviso / 🔵 sugestão. Output vai no comentário do PR — obrigatório.
→ Todo dev
🧪
QA Agent
Quando: Após a US ser desenvolvida
Cola os ACs da US. Agente gera plano de testes com casos manuais e automatizáveis, edge cases fiscais e de multi-tenancy. Equipe implementa os automatizáveis.
→ QA / SDET
🔒
Security Agent
Quando: A qualquer momento
Cola código, endpoint ou configuração suspeita. Agente retorna checklist de segurança categorizado. Útil especialmente em código fiscal e de autenticação.
→ Qualquer pessoa
🧠
Docs Agent
Quando: Após decisões de negócio
Cola a decisão técnica ou a regra de negócio que foi discutida. Agente gera documento canônico, ADR ou glossário de domínio pronto para revisão.
→ Guardião de Domínio

Execução › Política Legado vs Novo
Política: Legado vs Novo Sistema
A linha divisória que libera o time do legado progressivamente. Sem uma política clara, o legado sempre vai parecer mais urgente que o novo.
O problema sem política: um bug em produção no legado sempre vai parecer mais urgente que uma feature no novo sistema. Sem regra clara, o time vai ser eternamente puxado para o passado.
A política — 3 regras simples
1
Novas features vão apenas para o novo sistema
Qualquer funcionalidade nova que um cliente solicitar será implementada no novo sistema — nunca no legado. Se o cliente ainda não migrou, ele espera ou migra para ter acesso.
2
Bugs no legado recebem patch só se forem críticos (P0)
Bug que causa perda de dados, vazamento de informação ou indisponibilidade total: patch no legado. Bug de comportamento incorreto mas não crítico: fica na fila de migração.
3
Cada semana o time dedica 70% ao novo e 30% ao legado
Os 30% cobrem suporte, patches críticos e ajuda na migração dos clientes. Se não houver demanda de legado, os 30% vão para o novo. Nunca o contrário.
Critério de migração dos 20 clientes
FaseCritérioAção
Módulo pronto no novoO módulo equivalente ao que o cliente usa foi implementado e testadoCliente entra na fila de migração
Migração assistidaScript de migração de dados (long→Guid) disponível e testadoDev acompanha a migração do cliente por 1 sprint
Período de rollback30 dias com acesso ao legado como contingênciaLegado em modo leitura — sem novas gravações
Confirmação de migraçãoCliente operando no novo sistema por 30 dias sem incidente críticoLegado descomissionado para aquele cliente
Prioridade de migração: clientes que usam apenas FIN + VEN + EST migram primeiro — são os módulos mais completos. Clientes com necessidades específicas de módulos ainda em desenvolvimento ficam por último.
Execução › Transição em 90 Dias
Plano de Transição — 90 Dias
Do modelo atual para o novo sem parar o que existe. Três fases de 30 dias, cada uma com entregas concretas.
As 3 fases
FASE 1 — Dias 1 a 30
Contenção e fundação
✓ Patches de segurança S1-S4 do Assessment (JWT, CORS, Sentry, Hangfire)
✓ Configurar .cursorrules com Context Agent no repositório
✓ Cada dev cria seus perfis de agente no Cursor
✓ Papéis comunicados ao time — sênior para de organizar o Jira sozinho
✓ PO começa a usar Requirements Agent nas próximas US
✓ DoR e DoD definidos e apresentados ao time
FASE 2 — Dias 31 a 60
Processo e qualidade
✓ Code Review Agent obrigatório em todo PR (sem exceção)
✓ QA Agent gerando casos de teste a partir dos ACs

✓ Planning Agent no refinamento semanal
✓ Primeira sprint com métricas medidas (lead time, cobertura)
✓ Bloco 6 (Compras) em andamento com o novo processo
FASE 3 — Dias 61 a 90
Aceleração e migração
✓ Retrospectiva do framework — ajustar prompts com base nos dados
✓ Primeiro cliente legado em migração assistida para o novo sistema
✓ Trilha de treinamento iniciada (ver epros-treinamento.html)
✓ Script long→Guid validado e documentado
✓ Métricas de 60 dias analisadas — o que funcionou, o que ajustar
✓ Bloco 7 (Infraestrutura / CI-CD) iniciado

Como funciona a revisão mensal
1ª sexta de cada mês — Retrospectiva do Framework (30 min)
1. Tech Lead apresenta as métricas do mês
2. Time identifica o que funcionou e o que travou
3. Uma ação concreta: ajustar um prompt de agente, mudar critério de DoR, etc.
4. Registro no Docs Agent → entry no changelog do processo
5. Próxima reunião começa com o resultado da ação anterior
O framework é vivo. Os prompts dos agentes melhoram com o uso. O DoR e DoD evoluem com o time. O objetivo não é ter um processo perfeito desde o primeiro dia — é ter um processo que melhora toda semana.
