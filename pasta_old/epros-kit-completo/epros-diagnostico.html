SAST — Análise Estática

Varredura automática e manual do código-fonte sem executá-lo. Identificou: segredos hardcoded, algoritmos de criptografia fracos, SHA-256 sem salt.

BOLA/IDOR — Broken Access Control

Achados Críticos › Segredos Expostos
Segredos & Credenciais Expostos
Chaves, tokens e senhas no código-fonte versionado. O histórico do Git preserva esses valores mesmo após remoção.
Ação imediata: esses valores já foram vistos — rotacionar agora não é suficiente sem também invalidar os tokens e chaves existentes que foram gerados com eles.
CRÍTICOJWT Secret hardcoded — chave de assinatura de todos os tokens
A chave que assina todos os tokens JWT do sistema está embutida como string literal no código-fonte. Qualquer pessoa com acesso ao repositório pode gerar tokens válidos para qualquer usuário de qualquer tenant — sem precisar de credenciais.
// epros_erp-main/Epros.ERP/src/Epros.ERP.API/Security/Settings.cs public static string Secret { get { return "94135860-E039-470C-9629-6B6635F42B03-23423mnsdfa-32423"; } } // Program.cs — uso da chave hardcoded var key = Encoding.ASCII.GetBytes(Settings.Secret); IssuerSigningKey = new SymmetricSecurityKey(key),
Security/Settings.cs Program.cs Epros.ERP.FN.API/Security/
Impacto: Geração de token admin para qualquer cliente. Acesso total ao sistema sem autenticação real.
✓ Correção: mover para variáveis de ambiente / HashiCorp Vault. Rotacionar e invalidar todos os tokens existentes. Bloquear no CI via gitleaks.
CRÍTICONOVO — AssessmentToken externo com validade de 100 anos e sem validação de lifetime
O serviço de integração com a API de gestão de clientes gera tokens com validade de 100 anos e tem a validação de tempo de vida explicitamente desabilitada. Um token gerado hoje é tecnicamente válido até 2126.
// epros_gestao_clientes/.../Services/TokenExternoService.cs Expires = DateTime.UtcNow.AddYears(100), ValidateLifetime = false, // validação de expiração desabilitada
Epros.ControleTenant.API/Services/TokenExternoService.cs
Impacto: Token vazado nunca expira. Uma credencial comprometida hoje dá acesso para sempre — sem possibilidade de expiração natural.
✓ Correção: TTL curto (15–60 minutos), refresh token rotativo, validação de lifetime obrigatória.
CRÍTICONOVO — AssessmentCredenciais administrativas hardcoded em endpoints
Endpoints da API DFe usam credenciais administrativas fixas no código para autenticação entre serviços. Qualquer pessoa que inspecione o código consegue se autenticar como administrador nessas APIs.
Epros.ERP.Dfe.API/Controllers/V1/AccountController.cs ApiObjects/ConfigApi.cs — TokenApiDfe fixo Epros.ControleTenant.API/ApiObjects/Settings.cs
Impacto: Bypass completo de autenticação na API fiscal. Qualquer ator com acesso ao repositório pode emitir NF-e em nome de qualquer cliente.
✓ Correção: substituir por OAuth2 client credentials flow com Keycloak. Sem credenciais no código.
Achados Críticos › Autenticação & Sessão
Autenticação & Sessão
Como usuários fazem login, como a sessão é mantida e os vetores de ataque que isso abre.
CRÍTICONOVO — AssessmentToken JWT armazenado no localStorage — vulnerável a XSS
O frontend armazena o token de autenticação, o tenantId e o empresaId no localStorage do navegador. Qualquer script XSS na página consegue ler essas informações e sequestrar a sessão completa — incluindo o contexto de tenant.
// epros_erp_front-main/app/stores/authStore.ts localStorage.setItem('authToken', token) localStorage.setItem('tenantId', tenantId) localStorage.setItem('empresaId', empresaId) // localStorage é acessível por qualquer JavaScript na página // Um XSS rouba token + tenant em 1 linha: localStorage.getItem('authToken')
app/stores/authStore.ts
Impacto: XSS + localStorage = sequestro completo de sessão com contexto de tenant. O atacante não precisa saber a senha — só precisa executar um script na página.
✓ Correção: migrar para cookie HttpOnly + Secure + SameSite=Strict. Token nunca acessível por JavaScript.
CRÍTICONOVO — AssessmentSenha armazenada e comparada em texto puro
No módulo de gestão de clientes, senhas são atribuídas diretamente às entidades sem hash. O AccountController compara senhas sem pipeline robusto de verificação. Isso significa que senhas estão em texto legível no banco de dados.
// epros_gestao_clientes/.../Entities/Cadastro/Usuarios/Usuario.cs this.Senha = senha; // texto puro — sem hash // epros_gestao_clientes/.../Controllers/v1/AccountController.cs if (usuario.Senha == senhaInformada) // comparação em texto puro
Entities/Cadastro/Usuarios/Usuario.cs Controllers/v1/AccountController.cs
Impacto: Um dump do banco de dados expõe todas as senhas de todos os usuários em texto legível. Sem necessidade de crack ou força bruta.
✓ Correção: Argon2id ou bcrypt com salt único por usuário. Rehash progressivo no próximo login para usuários existentes.
ALTOSHA-256 sem salt para hash de senhas no ERP principal
O ERP principal usa SHA-256 com parâmetros fixos para hash de senhas. SHA-256 é um algoritmo de propósito geral — rápido demais para hash de senha. Sem salt único por usuário, é vulnerável a rainbow tables e ataques de dicionário pré-computados.
// epros_erp-main/.../Helpers/Security.cs SHA256.Create().ComputeHash(Encoding.UTF8.GetBytes(senha)) // SHA-256 sem salt = rainbow table ataca todas as senhas de uma vez // Algoritmos corretos: Argon2id, bcrypt, PBKDF2
Helpers/Security.cs
Impacto: Em caso de vazamento do banco, todas as senhas podem ser quebradas em horas com hardware comum.
ALTOSem MFA, sem rate limit, sem revogação de token
O endpoint de login não tem limite de tentativas por IP ou usuário. Não há multi-fator obrigatório. Não há mecanismo de revogar um token antes de sua expiração — uma sessão comprometida continua válida até o token expirar.
Impacto: Credencial fraca = acesso permanente. Sem como forçar logout de sessão ativa comprometida. Força bruta sem bloqueio.
✓ Correção: rate limit no login, MFA obrigatório para admin, refresh token rotativo com revogação via Redis.
Achados Críticos › Multi-tenancy
Falhas de Isolamento Multi-tenant
O maior risco de um SaaS B2B: um cliente acessar dados de outro. Encontramos múltiplos vetores para isso acontecer.
Tenant breakout é o tipo de incidente que encerra contratos, gera processo judicial por LGPD e destrói a reputação do produto. Esses achados precisam ser tratados antes de qualquer crescimento de base de clientes.
CRÍTICOTenantIdStatic — variável estática global compartilhada entre requests
O TenantId é armazenado como propriedade static na classe TenantData. Em .NET, variáveis estáticas são compartilhadas entre todas as threads do processo. Em um servidor com múltiplos requests concorrentes, o TenantId de um request sobrescreve o de outro.
// epros_erp-main/Epros.ERP.Shared/Providers/TenantData.cs public class TenantData { public string TenantId { get; set; } = string.Empty; public static string TenantIdStatic { get; set; } = string.Empty; // ↑ STATIC = compartilhado entre TODOS os requests simultâneos // Thread 1 (Tenant A): TenantIdStatic = "tenant-a" // Thread 2 (Tenant B): TenantIdStatic = "tenant-b" ← sobrescreve // Thread 1 lê agora: TenantIdStatic = "tenant-b" ← VAZAMENTO }
Epros.ERP.Shared/Providers/TenantData.cs
Impacto: Em picos de carga com múltiplos tenants simultâneos, dados de um cliente ficam visíveis para outro. Impossível detectar sem monitoramento específico.
✓ Correção: ITenantProvider via DI scoped (já implementado no novo sistema). Nunca static para contexto de request.
CRÍTICONOVO — AssessmentIgnoreQueryFilters() em fluxo sensível de importação
O serviço de importação de XMLs usa IgnoreQueryFilters() explicitamente — desabilitando o filtro de tenant para aquela query. Isso significa que a query retorna dados de todos os tenants, não apenas do tenant atual.
// epros_erp-main/.../Services/importacaoXmlService.cs var documentos = _context.DocumentosFiscais .IgnoreQueryFilters() // ← bypass explícito do filtro de tenant .Where(d => d.ChaveNfe == chave) .ToList(); // Retorna documentos de TODOS os tenants — não só do atual
Services/importacaoXmlService.cs
Impacto: Um XML de NF-e de outro cliente pode ser encontrado e processado no contexto errado. Dados fiscais cruzados entre clientes.
✓ Correção: revisar todos os usos de IgnoreQueryFilters(). Permitir apenas em serviços administrativos auditáveis, com teste específico de isolamento.
CRÍTICONOVO — AssessmentClienteController sem enforcement de TenantId — BOLA/IDOR
O controller de clientes no módulo de gestão realiza operações por ID sem validar consistentemente se o recurso pertence ao tenant do usuário autenticado. Um usuário pode trocar o ID na requisição e acessar dados de cliente de outro tenant.
Epros.ControleTenant.API/Controllers/v1/ClienteController.cs app/stores/authStore.ts — tenantId no cliente
Impacto: Tenant breakout via IDOR — trocar um ID na URL dá acesso a dados de qualquer outro cliente.
✓ Correção: todas as operações por ID verificam se o recurso pertence ao TenantId do claim JWT — nunca confiar no tenantId enviado pelo cliente.
ALTOSem QueryFilter automático — isolamento depende de disciplina manual
Não há QueryFilter global no DbContext que filtre automaticamente por tenant. Cada dev precisa lembrar de adicionar o WHERE manualmente em cada query. Uma query esquecida expõe todos os dados de todos os clientes.
Impacto: Basta um PR mal revisado para criar um endpoint que retorna dados de todos os tenants. Isso acontece — especialmente em equipes sem padrão documentado.
Achados Críticos › Superfície Exposta
Superfície de Ataque Exposta
Pontos de entrada abertos que ampliam o alcance de qualquer ataque.
CRÍTICOCORS aberto para qualquer origem em produção
As três APIs permitem requisições de qualquer origem, qualquer método e qualquer header. Isso permite que sites maliciosos façam chamadas autenticadas à API em nome de usuários logados — via CSRF ou abuso de credenciais.
// epros_erp-main/Epros.ERP.API/Program.cs app.UseCors(x => x .AllowAnyOrigin() .AllowAnyMethod() .AllowAnyHeader() ); // epros_erp-main/Epros.Erp.RealTime.API/Program.cs — mesmo padrão // epros_gestao_clientes/.../Program.cs — mesmo padrão
Epros.ERP.API/Program.cs Epros.Erp.RealTime.API/Program.cs Epros.ControleTenant.API/Program.cs
✓ Correção: allowlist por domínio por ambiente (dev/staging/prod). Nenhuma origem genérica.
CRÍTICONOVO — AssessmentHub SignalR sem autenticação — API RealTime aberta
A autenticação do hub de vendas em tempo real foi comentada no código. Qualquer cliente consegue se conectar ao hub e receber ou enviar eventos de venda sem estar autenticado.
// epros_erp-main/Epros.Erp.RealTime.API/Program.cs // .RequireAuthorization() ← comentado — autenticação desabilitada app.MapHub<VendaHub>("/hubs/venda");
Epros.Erp.RealTime.API/Program.cs
Impacto: Acesso anônimo a eventos de venda em tempo real. Possível injeção de eventos falsos ou interceptação de dados de transação.
✓ Correção: reabilitar RequireAuthorization() no hub. Validar tenantId no contexto de cada conexão.
ALTONOVO — AssessmentDashboard Hangfire sem autenticação real em produção
O painel de administração do Hangfire (onde ficam todos os jobs agendados) tem o filtro de autorização implementado de forma que é efetivamente aberto em produção. Qualquer pessoa pode acessar, visualizar e disparar jobs administrativos.
Epros.ControleTenant.API/Program.cs — HangfireAuthFilter
Impacto: Execução indevida de jobs como geração de faturas, envio de e-mails em massa, processamento de webhooks. Fraude operacional.
✓ Correção: autenticação forte + autorização por role + restrição por IP de origem no painel administrativo.
ALTOSem rate limit em endpoints críticos
Nenhum dos endpoints de login, emissão de NF-e ou operações financeiras tem limite de requisições por IP ou por usuário. Um atacante pode fazer chamadas ilimitadas sem ser bloqueado.
Impacto: Força bruta no login, abuso de API de emissão fiscal, denial of service por volume de requisições.
Achados Altos › PII em Logs & Telemetria
PII em Logs & Telemetria
Dados pessoais sendo registrados em locais onde não deveriam estar — violação direta de LGPD e PCI DSS.
ALTONOVO — AssessmentsendDefaultPii: true no Sentry — dados pessoais para serviço de terceiro
O Sentry (serviço de monitoramento de erros externo) está configurado para enviar automaticamente todos os dados pessoais identificáveis — CPF, e-mails, nomes, IPs — para os servidores do Sentry. Isso é uma violação direta da LGPD, que exige consentimento e contrato de processamento (DPA) para compartilhamento com terceiros.
// epros_erp_front-main/sentry.client.config.ts Sentry.init({ dsn: "...", sendDefaultPii: true, // ← envia CPF, e-mail, IP, headers para Sentry });
sentry.client.config.ts
Impacto: Dados pessoais de 20+ clientes sendo enviados para serviço de terceiro sem base legal explícita. Multa LGPD de até 2% do faturamento ou R$50M por infração.
✓ Correção: sendDefaultPii: false imediato. Configurar beforeSend para sanitizar dados sensíveis antes de enviar ao Sentry.
ALTONOVO — AssessmentLog de payload completo com dados de tenant e financeiros
Dois controllers registram o payload HTTP completo nos logs — incluindo CNPJ, dados fiscais e informações financeiras de tenants. Os logs são gravados em arquivo no servidor sem controle de acesso adequado.
Controllers/V1/TenantsController.cs — jsonRecebido/jsonGerado MercadoPagoWebhookController.cs — body completo do webhook
Impacto: Dados financeiros e pessoais em arquivos de log — LGPD. Qualquer pessoa com acesso ao servidor lê transações de todos os clientes.
✓ Correção: mascaramento global de PII (CPF, CNPJ, dados bancários) antes de qualquer sink de log. Nunca logar payload completo.
ALTOLogs gravados em wwwroot — potencialmente acessíveis via HTTP
Os logs são gravados dentro do diretório wwwroot da aplicação, que é o diretório de arquivos estáticos servidos via HTTP. Dependendo da configuração do servidor, os arquivos de log podem ser acessíveis via URL direta.
// Program.cs .WriteTo.File(@$"wwwroot/Logs/Log_{DateTime.Now:dd-MM}.txt")
Program.cs — Serilog configuration
Impacto: https://api.empresa.com/Logs/Log_01-06.txt pode estar publicamente acessível com todos os logs do dia.
Achados Altos › Criptografia Frágil
Criptografia & Gestão de Senhas Frágil
Algoritmos inadequados para o propósito, sem salt e com parâmetros fixos.
ALTOSHA-256 para hash de senha — sem salt, sem fator de custo
SHA-256 é um algoritmo de hash criptográfico de propósito geral — projetado para ser rápido. Para senha, isso é uma falha: um atacante pode testar bilhões de combinações por segundo. Sem salt único por usuário, rainbow tables pré-computadas atacam todas as senhas de uma vez.
// epros_erp-main/.../Helpers/Security.cs SHA256.Create().ComputeHash(Encoding.UTF8.GetBytes(senha)) // SHA-256 sem salt = mesma senha = mesmo hash para todos os usuários // Rainbow table para "123456" quebra todos os usuários com essa senha // O que deveria ser usado: Argon2id / bcrypt / PBKDF2 com salt único por usuário
Helpers/Security.cs
Impacto: Em um vazamento do banco, 100% das senhas ficam expostas em horas com hardware de consumidor.
✓ Correção: Argon2id para senhas novas. Rehash progressivo no próximo login para usuários existentes. Sem quebra de compatibilidade.
ALTONOVO — AssessmentJWT com algoritmo simétrico (HS256) — única chave para todos os tenants
O sistema usa JWT com HS256 (HMAC-SHA256) — um algoritmo simétrico onde a mesma chave é usada para assinar e verificar tokens. Isso significa que a API que verifica tokens também pode criar tokens. Em arquitetura de múltiplas APIs, isso aumenta a superfície de ataque.
Impacto: Qualquer uma das 3 APIs com a chave pode forjar tokens para as outras. Com a chave hardcoded, o problema é total.
✓ Correção: migrar para Keycloak com RS256 (assimétrico). A chave privada fica apenas no Keycloak — as APIs verificam com a chave pública.
Diagnóstico › Arquitetura
Problemas de Arquitetura
Problemas estruturais que tornam o sistema difícil de manter, impossível de testar e arriscado de escalar.
MÉDIO-ALTOControllers com 3.500–4.800 linhas — lógica de negócio no HTTP handler
Os controllers não são roteadores — contêm toda a lógica de negócio, acesso ao banco, cálculos fiscais e chamadas externas. O CompraController tem ~4.784 linhas — 32× acima do limite saudável de 150 linhas.
CompraController.cs → 191.388 bytes ≈ 4.784 linhas (32× acima do limite) VendaController.cs → 143.706 bytes ≈ 3.592 linhas (24× acima) VendaNfeController.cs → ~2.739 linhas (18× acima) ContasAPagarController → 41.637 bytes ≈ 1.040 linhas (7× acima) // Um controller saudável: 50–150 linhas
Impacto: Mudança em qualquer ponto pode quebrar algo em 4.784 linhas. Impossível testar isoladamente. Onboarding de novos devs leva semanas só para entender um módulo.
MÉDIO3 APIs sem contrato formal de integração
As 3 APIs (ERP, DFe, RealTime) se comunicam via HTTP sem OpenAPI validado entre elas e sem testes de integração. Uma mudança de contrato em uma API quebra as outras silenciosamente.
Impacto: Deploy de uma API pode quebrar as outras. A equipe descobre quando o cliente reporta o problema.
MÉDIOIDs long sequenciais — offline e mobile impossíveis
IDs gerados pelo banco (long/int) exigem conexão para criar qualquer registro. PDV offline e app mobile verdadeiros são impossíveis com essa arquitetura.
Impacto: Cada tentativa de resolver isso gerou gambiarras no PDV. Mobile nativo exige reescrita da camada de dados.
MÉDIOBlazor WASM como terceira stack — time dividido
