Guia de Onboarding

Documentação passo a passo para preparação do ambiente de desenvolvimento local, inicialização da stack e convenções técnicas de contribuição de código.

Inicialização do Ambiente Local

Para começar a contribuir com o ecossistema Epros, siga o checklist de instalação de dependências e subida dos serviços Docker locais.

STEP 1

Instalar Pré-requisitos

Instale as seguintes ferramentas na sua máquina de desenvolvimento local:

  • SDK .NET 8.0 — Necessário para compilar o backend C#.
  • Docker & Docker Desktop — Gerencia os containers locais da infraestrutura.
  • Node.js 18+ & NPM — Necessário para o frontend desktop / web `Epros.App` (Nuxt 3).
  • Expo CLI — Para rodar o aplicativo mobile `/Epros.Mobile` (React Native).
STEP 2

Subir a Infraestrutura (Docker Compose)

Navegue até a raiz do projeto e execute o comando abaixo para iniciar todos os containers de infraestrutura local em background:

docker-compose up -d

Este comando irá inicializar os serviços:

PostgreSQL 16Porta 5432epros / epros_dev_password
Keycloak 24Porta 8080admin / admin (auto-importa realm e clients)
HashiCorp VaultPorta 8200Token: epros-dev-token
MinIO StoragePorta 9000/9001epros_minio / epros_minio_password
Valkey 7Porta 6379Sem autenticação por padrão em desenvolvimento
STEP 3

Inicializar o Backend & Migrations

Para executar o monólito modular C# e aplicar todas as migrações automaticamente no banco PostgreSQL 16 local de desenvolvimento, utilize:

dotnet run --project src/API/Epros.API/Epros.API.csproj

Nota: O projeto está configurado para executar migrações de banco programaticamente em tempo de inicialização em ambiente `Development`. Os logs do console detalham o progresso de migração de cada DbContext.

Padronização de Código & Formatação

Para garantir a consistência do código C#, todas as submissões de Pull Requests passam por verificação automática de estilo. Cumpra os requisitos locais antes de commitar:

  • 1
    Verificação de Formatação: Execute o comando do SDK dotnet para alinhar e indentar automaticamente o código de acordo com o padrão do projeto:
    dotnet format
  • 2
    Warnings as Errors: O build em Release compila com a tag `-warnaserror` ativada. Códigos contendo avisos do compilador (ex: variáveis não utilizadas ou nulos não tratados) causam falha imediata no CI. Resolva todos os warnings localmente.
Fluxo de Trabalho de Branches (Git Flow)

As ramificações do repositório seguem um fluxo estruturado simplificado para garantir estabilidade contínua nas ramificações principais.

main
← merge (Release PR) ←
develop
← merge (Review PR) ←
feature/nome-recurso
  • `main` — Ramo de produção. Protegida contra pushes diretos. Só aceita alterações via PR a partir de `develop`.
  • `develop` — Ramo de integração. Onde as features concluídas são testadas de forma integrada.
  • `feature/*` ou `bugfix/*` — Ramificações de trabalho criadas a partir de `develop`.
Convenção de Commit Semântico

Os títulos de commit do projeto devem respeitar a especificação do Conventional Commits para permitir a geração de Changelogs automáticos. O formato é:

<tipo>(<escopo-opcional>): <descrição curta em português>
Tipo de Commit Finalidade Exemplo prático
feat Criação de nova funcionalidade ou endpoint. feat(vendas): adiciona fechamento de caixa do pdv
fix Correção de bug, falha ou comportamento incorreto. fix(estoque): corrige calculo do custo medio ponderado
docs Apenas alterações em documentação (.md, .html). docs(onboarding): cria guia de setup do desenvolvedor
refactor Alteração de código que não corrige bug nem adiciona funcionalidade. refactor(shared): simplifica estrutura de notificacoes do flunt
test Adição ou correção de testes unitários ou de integração. test(financeiro): adiciona testes de outbox do contas a pagar
chore Atualização de dependências, builds ou scripts internos. chore(infra): atualiza versao do postgres no docker-compose
Pipeline Automatizada de CI/CD

Toda submissão de código a ramos remotos (`develop` e `main`) dispara a esteira de validação em segundo plano no GitHub Actions.

IMPORTANTE: O pipeline de CI/CD é bloqueante. Se qualquer um dos passos abaixo falhar, a mesclagem (merge) do Pull Request não será permitida.
  • 1
    Restore & Format Check: O runner faz o download das dependências e executa o validador de estilo `dotnet format --verify-no-changes`. Se o desenvolvedor não formatou o código localmente, o pipeline falha.
  • 2
    Compilação Restrita: A compilação é executada em modo Release (`dotnet build -warnaserror`). Avisos de compilação bloqueiam o deploy.
  • 3
    Suíte de Testes: Executa toda a suíte de testes xUnit, inicializando containers reais via Testcontainers para garantir a integridade das políticas de banco e RLS.
  • 4
    Segurança SAST: Rodam os scanners **Gitleaks** (identificação de segredos e tokens expostos) e **Trivy** (busca por vulnerabilidades de dependências com severidade HIGH e CRITICAL).
