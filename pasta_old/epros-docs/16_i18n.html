Internacionalização & Localização

Diretrizes arquiteturais para suporte a múltiplos idiomas, moedas, fusos horários e adaptações fiscais por país no ecossistema Epros.

Estratégia de Locales no Frontend e Mobile

O suporte a múltiplos idiomas é gerenciado no lado do cliente por meio de dicionários estáticos integrados aos bundles das aplicações.

Nuxt 3 (Nuxt i18n) Web/Desktop
Na aplicação web e desktop (`Epros.App`), o gerenciamento é realizado pelo plugin `@nuxtjs/i18n`. Os dicionários JSON são carregados dinamicamente via lazy loading sob demanda com base no locale ativo.
// nuxt.config.ts i18n: { locales: [ { code: 'pt', iso: 'pt-BR', file: 'pt-BR.json', name: 'Português (Brasil)' }, { code: 'en', iso: 'en-US', file: 'en-US.json', name: 'English (US)' }, { code: 'es', iso: 'es-ES', file: 'es-ES.json', name: 'Español (España)' } ], defaultLocale: 'pt', lazy: true, langDir: 'locales/' }
React Native (expo-localization) Mobile/PDV
O aplicativo móvel `Epros.Mobile` utiliza `i18n-js` em conjunto com `expo-localization` para ler o locale nativo do sistema operacional e carregar a tradução correspondente com fallback seguro para `pt-BR`.
Representação de Valores Regionais e Tempo

Garantia de consistência de dados contábeis e representação correta de datas para usuários distribuídos globalmente.

Timezone em Armazenamento e Exibição Arquitetura
Banco de Dados (UTC): Todo campo de data e hora deve ser salvo no PostgreSQL como `timestamp with time zone` (ou mapeado como UTC no EF Core).

Client-Side conversion: A API envia strings no padrão ISO 8601 UTC. O cliente intercepta e formata para o fuso horário configurado nas preferências do inquilino (ou do dispositivo).
Padrões de Formatação Regional UX
A formatação utiliza a API nativa `Intl` do JavaScript para formatação de números, moedas e datas baseados no locale atual:
LocaleDataNúmeroMoeda (Exemplo)
pt-BR09/06/20261.250,50R$ 1.250,50
en-US06/09/20261,250.50$1,250.50
es-ES09/06/20261 250,501.250,50 €
Dados Dinâmicos Multilíngues no PostgreSQL

Para cadastros cadastrados pelos usuários (ex: descrição de planos ou nomes de produtos), adota-se uma estratégia de tradução transacional no banco.

JSONB Localizado vs. Tabela Transacional PostgreSQL
Para evitar joins excessivos e garantir performance de leitura nas queries de catálogo, os campos traduzíveis de entidades estáticas utilizam colunas do tipo jsonb contendo chave/valor do locale.

Estrutura de dados (Exemplo em JSONB):
{ "pt-BR": "Serviço de Assinatura Platinum", "en-US": "Platinum Subscription Service", "es-ES": "Servicio de Suscripción Platinum" }
Query de Leitura Eficiente:
SELECT id, nome->>'pt-BR' AS nome_localizado FROM plataforma.planos;
Abstração de Motores de Impostos (Tax Engines)

Isolamento das complexidades e particularidades da regulação fiscal brasileira de outros mercados internacionais.

Padrão Adapter no Faturamento C# / DDD
O módulo fiscal expõe uma interface abstrata de faturamento `ITaxCalculator`. Para cada país de operação, implementa-se um adaptador de cálculo e transmissão específico.

* BrTaxCalculator: Integrado com a biblioteca `Hercules.NET` para emissão de NF-e/NFC-e e cálculo de ICMS, IPI, PIS, COFINS. * EuTaxCalculator (VAT): Efetua o cálculo de imposto sobre valor agregado de acordo com as regras de balanço intra-comunitário da UE. * UsTaxCalculator (Sales Tax): Conecta com engines de cálculo de Sales Tax estadual/municipal americano (ex: Avalara).
