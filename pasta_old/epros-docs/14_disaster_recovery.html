Plano de Disaster Recovery

Políticas e procedimentos operacionais para recuperação da plataforma Epros diante de falhas críticas, desastres geográficos ou corrupção de dados.

Metas de Continuidade de Negócios (BCP)

O plano de continuidade de negócios garante limites estritos para indisponibilidade e perda de dados, alinhados com os requisitos regulatórios fiscais e de segurança.

RTO (Recovery Time Objective)

4 Horas

Tempo máximo tolerado para restabelecimento total da operação da plataforma Epros após declaração de desastre geográfico no datacenter primário.

RPO (Recovery Point Objective)

10 Minutos

Limite de perda aceitável de transações financeiras e operacionais de venda/estoque dos inquilinos (viabilizado por arquivamento WAL contínuo).

Escopo de Proteção e Severidade

São cobertos pelo plano de contingência os seguintes cenários extremos:

  • Falha Geográfica Total: Indisponibilidade permanente ou severa de uma região de nuvem (ex: AWS us-east-1).
  • Ransomware ou Sabotagem: Criptografia maliciosa de volumes de dados ou servidores centrais.
  • Corrupção Lógica de Dados: Bugs catastróficos no monólito modular ou script manual incorreto alterando tabelas produtivas.
Arquitetura de Redundância e Proteção

A arquitetura de dados do Epros utiliza uma abordagem híbrida de replicação em tempo real combinada com backups pontuais e registros transacionais.

REGRA DE SEGURANÇA: Em produção, as chaves mestras de abertura (Unseal Keys) do Vault são divididas em 5 chaves. São necessárias no mínimo 3 chaves (threshold = 3) para abrir o Vault após reinicialização. Cada chave deve estar em posse de um administrador de segurança sênior diferente.
Manual Passo a Passo de Recuperação Física

Procedimento técnico emergencial para reconstrução do banco de dados PostgreSQL 16 e aplicação de Point-in-Time Recovery (PITR).

1. Restaurar Backup Físico Base

Para inicializar o restore de desastre, baixe o último backup base físico para a pasta de dados do PostgreSQL:

# Parar o serviço do banco de dados
systemctl stop postgresql-16

# Limpar pasta de dados corrompida (preservar configurações)
rm -rf /var/lib/postgresql/16/main/*

# Baixar e extrair o backup físico base do MinIO S3
aws s3 cp s3://epros-backups/postgres/base-latest.tar.gz - | tar -xzvf - -C /var/lib/postgresql/16/main/
2. Configurar Point-in-Time Recovery (PITR)

Crie o arquivo de controle para instruir o PostgreSQL a entrar em modo de recuperação transacional e defina a data-alvo limite de restore (RPO de 10 min):

# Criar sinalizador de recovery
touch /var/lib/postgresql/16/main/recovery.signal

# Adicionar configurações em postgresql.conf ou no bloco de recovery:
restore_command = 'cp /mnt/wal_archive/%f %p'
recovery_target_time = '2026-06-09 10:45:00 UTC'
recovery_target_action = 'promote'
3. Reiniciar Banco de Dados & Promover

Inicie o banco de dados. Ele processará todos os logs WAL até o horário configurado e estará pronto para escrita:

systemctl start postgresql-16
# Monitorar logs de recuperação no syslog/postgresql.log
tail -f /var/log/postgresql/postgresql-16-main.log
Manual de Simulações Periódicas (DR Drills)

Para garantir a eficácia do plano de continuidade de negócios, a equipe DevOps executa simulações semestrais obrigatórias.

  • 1
    Declaração de Desastre Simulado: O coordenador do teste corta as rotas de tráfego de rede para a região produtiva principal simulando falha total.
  • 2
    Failover de DNS (Caddy): O proxy Caddy e o roteador de DNS (Cloudflare) redirecionam o tráfego do gateway `/api/v1` para a região de contingência (Cold Standby).
  • 3
    Verificação de Integridade de Tenants: O comando `dotnet run` reinicia os monólitos na região secundária. Varreduras de integridade automática verificam conexões e garantem que o isolamento RLS está ativo em todas as tabelas.
  • 4
    Validação de Métricas: O tempo total do processo de restore e failover é cronometrado para certificar que o RTO real permaneceu abaixo das 4 horas acordadas.
