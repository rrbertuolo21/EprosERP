Achados de Severidade Crítica (🔴 Risco Ativo)

Vulnerabilidades de alta severidade que permitiam invasão de dados, bypass de autenticação e vazamento de informações confidenciais entre inquilinos no legado.

Segredos
Chave de Assinatura JWT (Settings.Secret) Hardcoded
A chave privada simétrica utilizada para assinar os tokens JWT de todas as sessões do ecossistema estava embutida como uma string literal no código. Qualquer ator com acesso ao repositório poderia falsificar um token administrativo válido para qualquer tenant.
// local: epros_erp-main/Epros.ERP.API/Security/Settings.cs public static string Secret { get { return "94135860-E039-470C-9629-6B6635F42B03-23423mnsdfa-32423"; } }
Impacto: Perda total de integridade. Acesso completo ao monólito como administrador por meio de bypass manual.
Solução Epros: Substituição por Keycloak 24 OIDC com verificação de assinatura assimétrica (RS256). Chave privada mantida no Keycloak.
Sessão
Token de API Externo Válido por 100 Anos
Os tokens gerados para comunicação de serviços satélites foram configurados com tempo de expiração de 100 anos, além de terem a validação de tempo de vida desabilitada na inicialização do middleware.
// local: Epros.ControleTenant.API/Services/TokenExternoService.cs Expires = DateTime.UtcNow.AddYears(100), ValidateLifetime = false, // Bypass de expiração
Impacto: Credenciais vazadas permaneciam ativas e utilizáveis indefinidamente no servidor.
Solução Epros: Implementação de tokens OIDC com TTL curto (15 minutos) e fluxo de rotação de refresh tokens.
Autenticação
Armazenamento de Senhas em Texto Puro
O banco de dados de gerenciamento de inquilinos salvava as senhas dos usuários sem qualquer hash criptográfico. A comparação de autenticação era feita por igualdade direta de strings.
// local: Epros.ControleTenant.API/Controllers/v1/AccountController.cs if (usuario.Senha == senhaInformada) { /* login efetuado */ }
Impacto: Vazamento de banco de dados expõe imediatamente as senhas de todos os super-administradores do SaaS.
Solução Epros: Hashing de senhas utilizando Argon2id com salting exclusivo por usuário no Keycloak.
Multi-tenancy
Tenant Breakout via Variáveis Estáticas Globais
O identificador de tenant do contexto de requisição era mantido em uma propriedade estática. Como variáveis estáticas no runtime do .NET compartilham estado entre threads sob concorrência, o TenantId de um usuário sobrescrevia o de outro sob cargas simultâneas.
// local: Epros.ERP.Shared/Providers/TenantData.cs public static string TenantIdStatic { get; set; } = string.Empty;
Impacto: Vazamento de dados em tempo real. Usuários lendo e modificando dados financeiros de outros inquilinos.
Solução Epros: Injeção de ITenantProvider resolvido via escopo HTTP (Scoped DI) acoplado ao `IHttpContextAccessor`.
Achados de Severidade Alta (🟡 Impacto Operacional)

Vulnerabilidades de média-alta criticidade que violavam regulações de privacidade como a LGPD e o PCI DSS devido a vazamento de PII em logs e telemetria de terceiros.

LGPD
Vazamento Automático de PII (sendDefaultPii) para o Sentry
A biblioteca do monitor de erros do frontend Nuxt 3 enviava dados privados de transação, cookies, headers e IP dos clientes finais em texto claro aos servidores externos de telemetria sem consentimento.
// local: epros_erp_front-main/sentry.client.config.ts Sentry.init({ dsn: "https://...", sendDefaultPii: true, // Vaza CPFs, e-mails e tokens de autorização });
Impacto: Multas severas de até 2% do faturamento por infração de vazamento de dados de privacidade (LGPD/GDPR).
Solução Epros: Configuração de `sendDefaultPii: false` e adição de gancho `beforeSend` para higienização e mascaramento de strings de CPF e chaves.
Segurança
Logs Gravados em wwwroot acessíveis via Web (Serilog File)
Os arquivos brutos de logs do sistema contendo informações operacionais eram salvos dentro do diretório `wwwroot` de conteúdo estático público das APIs.
// local: Program.cs .WriteTo.File(@"wwwroot/Logs/Log_Dev.txt")
Impacto: Exposição direta. Qualquer atacante poderia baixar os logs e ler as credenciais e dados dos clientes se a indexação estivesse habilitada.
Solução Epros: Logs centralizados via OpenTelemetry exportando para Loki/Tempo em rede isolada, removendo gravação física do wwwroot.
Criptografia
Algoritmo SHA-256 Sem Salt para Senhas do ERP
Embora o ERP principal realizasse hash de senha (ao contrário do Blazor que salvava em texto puro), ele utilizava SHA-256 sem salt exclusivo por usuário. Isso permitia que senhas iguais gerassem hashes idênticos.
Impacto: Suscetível a ataques de engenharia reversa rápidos baseados em tabelas de arco-íris (Rainbow Tables).
Solução Epros: Keycloak centralizado gerenciando criptografia de senha e delegando ao monólito apenas o Bearer JWT.
Débitos de Arquitetura & Qualidade do Legado

Os problemas estruturais que inviabilizavam a manutenção de rotina e causavam bugs operacionais frequentes em ambiente de produção.

Arquitetura

Controllers com Volume Excessivo

Handlers HTTP carregavam toda a lógica de persistência e validação. O controller CompraController.cs registrava incríveis 4.784 linhas de código de forma monolítica (32× acima do saudável).

CompraController.cs (~4.7k lines)
VendaController.cs (~3.5k lines)
Qualidade

Zero Testes de Integração

O repositório principal do ERP possuía apenas testes isolados em classes utilitárias de cálculos fiscais. Não havia suite de testes de concorrência ou de validação de isolamento de tenants.

Epros.ERP.API -> 0 testes
Epros.ERP.Datas -> 0 testes
Evidência Operacional de Débito
Ausência de Observabilidade: Os erros no legado eram logados localmente e sem CorrelationId. A equipe não possuía dashboard de monitoramento (Prometheus/Grafana) e descobria falhas graves por meio de ligações telefônicas dos clientes em produção.
Resiliência

Acoplamento Estrito entre APIs

As chamadas de integração síncronas entre as 3 APIs eram feitas sem controle de timeouts ou circuit breakers. Falha na transmissão de XML na API de DFe bloqueava a API principal de vendas.

Modelo de Dados

IDs Long Sequenciais no Banco

Todas as PKs eram geradas via banco auto-incremento. Impedia o desenvolvimento de operações offline locais ou sincronização delta no aplicativo móvel.

Plano de Contenção de Risco (30 dias)

Checklist de patches de segurança de curto prazo aplicados diretamente no sistema legado para mitigar riscos enquanto a reengenharia para o novo monólito avançava.

✓ Semana 1: Contenção de Segredos & Telemetria
Mover JWT Secret do settings para variáveis de ambiente; desabilitar sendDefaultPii no Sentry do Nuxt; restringir a política de CORS nas APIs para allowlist de produção.
✓ Semana 2: Blindagem de Autenticação & Sessão
Remover tokens simétricos de longa duração; migrar tokens de autenticação local no frontend para cookies seguros HttpOnly; integrar Argon2id para hash de senhas novas.
✓ Semana 3: Isolamento Multi-tenant & Higienização
Auditar uso de IgnoreQueryFilters() e remover a propriedade `TenantIdStatic`; configurar Serilog Enricher para mascarar CPFs e e-mails em arquivos de log.
✓ Semana 4: Gates de CI/CD & Resiliência
Configurar o pipeline do GitHub Actions para bloquear merges com falha em testes; introduzir o Polly para lidar com retentativas com jitter nas chamadas HTTP.
Veredicto e Correções Estruturais por Design

Legado (Problema)

• Senha em texto puro no banco
• Variável static para TenantId
• Token de 100 anos no localStorage
• Controllers gigantes sem teste
• SQL Server e licenciamento caro

Novo Monólito (Solução por Design)

• Keycloak + hash robusto Argon2id
• ITenantProvider scoped via DI
• Cookies HttpOnly + JWT curto assimétrico
• CQRS vertical slices + Testcontainers
• PostgreSQL 16 com RLS nativo

Conclusão: Os remendos de segurança mitigaram os riscos urgentes nos 20 clientes em produção, mas a reengenharia total baseada no monólito modular e Row-Level Security é a única resposta sustentável para o sucesso do produto.
