Runbook & Disaster Recovery

Diretrizes operacionais e procedimentos técnicos para sustentação do ambiente multi-tenant Epros. Garanta alta disponibilidade, segurança e conformidade regulatória nas operações diárias.

Manual de Mitigação de Incidentes Críticos

Passo a passo operacional para tratamento de alertas automáticos disparados pelo monitoramento centralizado do Epros (OpenTelemetry + Prometheus + Grafana).

Sev 1 - Crítica Detecção de Vazamento de Tenant (TenantLeakDetected) ▼
CRÍTICO: Indica que uma query interceptada ou processamento tentou acessar dados de um TenantId sem o cabeçalho correto ou com token pertencente a outro inquilino. Risco direto de violação de RLS e conformidade LGPD.
  • 1
    Identifique a origem do vazamento via traceId no Grafana Tempo ou Loki com a consulta: {app="epros-api"} |="TenantLeakDetected".
  • 2
    Revogue imediatamente a sessão do usuário ou aplicação causadora no painel do Keycloak para cessar requisições.
  • 3
    Verifique se o interceptor TenantRlsInterceptor está ativo no DbContext envolvido. Rode o script de auditoria no PostgreSQL para garantir que o RLS está ativo para a tabela:
    SELECT tablename, rowsecurity FROM pg_tables WHERE schemaname = 'vendas';
  • 4
    Corrija o vazamento no código e registre o incidente na fila de conformidade LGPD/ANPD em menos de 24h.
Sev 1 - Crítica Serviço de Autenticação Offline (KeycloakDown) ▼
CRÍTICO: A API do monólito perdeu conectividade com o cluster Keycloak. Usuários novos não conseguem logar e tokens não podem ser validados.
  • 1
    Valide a integridade física do container/cluster Keycloak. Se estiver rodando localmente/Docker, execute: docker compose ps keycloak.
  • 2
    Verifique os logs do Keycloak para estouro de pool de conexões do PostgreSQL: docker compose logs keycloak --tail=100.
  • 3
    Caso o Keycloak esteja offline por falha de infraestrutura, os aplicativos clientes (Epros.App e Epros.Mobile) devem ser instruídos a usar as credenciais locais em cache (modo contingência offline) para preservar a operação dos caixas PDV.
  • 4
    Restaure o serviço e limpe os caches de tokens expirados no Valkey executando: valkey-cli FLUSHDB.
Sev 2 - Alta Atraso Crítico no Quartz Outbox Worker (OutboxProcessingDelay) ▼
AVISO: O tempo médio de processamento de mensagens na tabela outbox_messages superou 5 minutos, gerando delay na faturamento de NF-es e geração de Contas a Receber.
  • 1
    Verifique mensagens travadas em falha contínua no PostgreSQL:
    SELECT id, event_type, tentativas, erro FROM vendas.outbox_messages WHERE processado_em IS NULL AND tentativas >= 5;
  • 2
    Se houver mensagens com erros de desserialização JSON ou timeouts de comunicação de rede com módulos externos (ex: SEFAZ, MercadoPago), registre o erro e resete temporariamente as tentativas para reprocessar após correção:
    UPDATE vendas.outbox_messages SET tentativas = 0, erro = NULL WHERE processado_em IS NULL;
  • 3
    Aumente o número de threads disponíveis no Quartz.NET se a fila estiver crescendo muito rápido devido a pico de vendas.

Política e Procedimento de Disaster Recovery

Planos de Contingência e Recuperação de Desastres para os dados armazenados nos schemas do PostgreSQL 16 e nos buckets do MinIO S3.

RTO (Recovery Time Objective)

Tempo máximo tolerado offline: 4 horas

Em caso de desastre físico no datacenter principal, o ambiente deve ser provisionado em zona alternativa e restabelecido com base nos backups em até 4 horas.

RPO (Recovery Point Objective)

Perda de dados tolerada: 10 minutos

A perda de transações comerciais não pode ultrapassar 10 minutos. Isso é mantido via Write-Ahead Log (WAL) archiving a cada 5 minutos.

Procedimento de Backup Automático
PostgreSQLBackup diário completo (pg_dumpall) comprimido e criptografado com GPG, enviado para MinIO S3 externo. Envio de WAL archives a cada 5 minutos para replicação incremental.
Vault SecretsBackup periódico do storage backend do HashiCorp Vault. As chaves de decodificação Unseal Keys são armazenadas separadamente por 3 administradores diferentes de acordo com o Shamir's Secret Sharing.
Arquivos GED (MinIO)Bucket replication em tempo real para cluster de redundância localizado em região geográfica distinta. Retenção fiscal de 5 anos ativada por política no S3.
Procedimento Passo a Passo de Restore em Caso de Desastre
  • 1
    Provisione uma nova instância de banco de dados PostgreSQL 16 limpa usando as receitas do Terraform/OpenTofu.
  • 2
    Recupere o backup base diário mais recente do S3 seguro executando:
    aws s3 cp s3://epros-backups/postgres/base-latest.sql.gz /tmp/base.sql.gz
  • 3
    Descomprima e aplique o backup base no banco recém-criado:
    gunzip -c /tmp/base.sql.gz | psql -U epros -d epros_prod
  • 4
    Aplique a sequência de logs transacionais (WAL archives) acumulados desde o backup diário para atingir o RPO de 10 minutos (Point-in-Time Recovery):
    pg_recvlogical --start -f /var/lib/postgresql/wal_archive/...
  • 5
    Suba os containers da API Gateway. O bootstrap automático (Program.cs) validará a integridade do banco e aplicará quaisquer migrations pendentes que não estavam no backup base.
Estratégias de Migração de Tier de Inquilinos

Procedimentos seguros para evolução e isolamento físico de inquilinos de acordo com o crescimento volumétrico e plano SaaS contratado.

Nível 1 - Shared

Múltiplos inquilinos residem no mesmo cluster de banco de dados compartilhando recursos e hardware. O isolamento lógico é garantido via RLS (Row-Level Security) no PostgreSQL.

Silver / Gold

Nível 2 - Dedicated

Tenant evolui para um banco de dados / schema exclusivo em cluster apartado para evitar o efeito "noisy neighbor" de outros inquilinos. Maior performance de IOPS.

Platinum / Enterprise

Nível 3 - Private

Migração física completa para ambiente exclusivo em nuvem privada ou infraestrutura on-premises de clientes corporativos com fortes requisitos regulatórios.

Custom / Corporativo
Roteiro de Migração: Nível 1 (Shared) para Nível 2 (Dedicated DB)
  • 1
    Agende a janela de manutenção e ative o modo de suspensão temporária do tenant via Painel SaaS Super Admin (altera status para Suspenso e impede escritas).
  • 2
    Extraia de forma isolada os dados do tenant de todos os schemas usando filtros de tenant_id. Exemplo de extração de vendas:
    pg_dump -U epros -d epros_prod -t 'vendas.vendas' --data-only --inserts --extra-float-digits=0 --where="tenant_id='tenant-exemplo'" > /tmp/tenant-vendas.sql
  • 3
    Crie a nova base de dados PostgreSQL dedicada para o tenant e execute a criação de tabelas rodando a API apontando para a nova string de conexão.
  • 4
    Importe os dados extraídos na nova base de dados.
  • 5
    No banco de catálogo global (Catalog Database), atualize a string de conexão (ConnectionString) e o tipo de infraestrutura do inquilino para dedicada.
  • 6
    Reative o inquilino no painel SaaS. O roteador dinâmico de conexões redirecionará todas as novas requisições daquele tenant para a nova base dedicada sem interrupção de serviço geral.
